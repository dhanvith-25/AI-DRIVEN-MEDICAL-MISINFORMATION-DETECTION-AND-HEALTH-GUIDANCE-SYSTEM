SECTION 1: PROJECT OVERVIEW
================================================================================
Project Purpose:
Satarka is an enterprise-grade, privacy-first, hybrid AI-powered healthcare platform designed to combat health misinformation, verify medical claims with live evidence, analyze personal lab reports through local OCR (Optical Character Recognition), perform AI-based symptom assessments, and manage longitudinal medical trends without transmitting sensitive patient data to third-party services.

Real-World Problem Solved:
1. Automated Misinformation Verification: Instantly checks online medical claims (e.g., "Antibiotics cure the common cold") against verified scientific datasets, live Tavily web search, Google Fact Check Tools API, domain WHOIS records, and SSL trust indicators.
2. Privacy-Preserving Lab Report Analysis: Extracts structured numerical laboratory measurements from uploaded PDFs and images locally using pypdf and pytesseract (Tesseract OCR), enabling patients to search, visualize trends, and ask natural language questions about their health data locally.
3. AI-Driven Symptom Evaluation: Uses Microsoft PubMedBERT embeddings (microsoft/BiomedNLP-PubMedBERT-base-uncased-abstract-fulltext) and Logistic Regression to match symptoms to disease profiles while giving risk levels, prevention steps, and clinical disclaimers.
4. Autonomous Dataset Continuous Fine-Tuning: Ingests high-confidence verified claims into a local Qwen2.5-0.5B-Instruct LoRA fine-tuning queue for domain-specific local LLM adaptation.

SECTION 2: PROJECT WORKFLOW & EXECUTION FLOW
================================================================================
Startup Flow:
1. app/main.py initializes FastAPI application with lifespan context.
2. init_db() in app/db.py executes SQLite DDL script creating all tables and applying migration columns.
3. SentenceTransformers (all-MiniLM-L6-v2) is loaded on demand; FAISS index (faiss_index.bin) and metadata (faiss_metadata.pkl) are loaded or rebuilt from verified_claims.

Execution Flow:
- User submits a claim -> Checked via health domain filter -> Predicted via TF-IDF Logistic Regression model.
- Deep verification -> Checked against FAISS vector index -> If Cosine Similarity >= 0.88, return VERIFIED_DATASET hit immediately -> Else, route query to LLM + Tavily web search -> Score evidence via 5-pillar mathematical validator -> If score >= 95%, auto-ingest into dataset.
- Report upload -> Saved locally -> pypdf / Tesseract OCR extracts text -> TF-IDF test classifier & regex parser extract measurements -> Persisted to SQLite -> Trend summary & Q&A generated.

SECTION 3: ARCHITECTURE ANALYSIS
================================================================================
Architectural Pattern: Clean Architecture with Layered Service Pattern and Hybrid Local/Cloud RAG Pipeline.

Layers:
- Presentation Layer: React 18 + Vite (App.jsx) + CSS.
- Controller Layer: FastAPI Router (app/main.py).
- Service Layer: validator.py, health_model.py, symptom_checker.py, personal_records.py, evidence_reasoner.py, llm.py, search.py.
- Data Layer: SQLite Engine (app/db.py), File Storage (data/personal_reports), FAISS Vector Index (app/dataset.py).
- AI/ML Layer: SentenceTransformers, PubMedBERT, Scikit-Learn Classifiers, Hugging Face TRL / BitsAndBytes / PEFT LoRA.

SECTION 7: API ENDPOINTS
================================================================================
- POST /health/predict : Predict health claim verdict using local ML model.
- POST /query : Execute RAG query verification with live web sources & validator scoring.
- POST /symptom-check : Analyze manually entered symptoms using the symptom dataset.
- POST /personal-reports/upload : Extract and save personal lab report measurements locally.
- GET /personal-reports/summary : Calculate longitudinal health metrics trends.
- POST /personal-reports/ask : Answer natural language questions on historical lab test changes.
- POST /dataset/search : Search top-K semantic vector matches in FAISS index.
- GET /report : Fetch historical verification audit log summary.
- POST /admin/review : Update claim review status for fine-tuning queue.
- POST /training/run : Trigger LoRA fine-tuning training job.

SECTION 10: SECURITY ANALYSIS
================================================================================
1. Local Data Privacy: All medical reports and extracted text remain 100% on local storage.
2. Path Traversal Protection: Absolute path resolving (.resolve()) verifies targets remain in designated directories.
3. Upload File Validation: Extension, MIME, byte size, PDF header, and Pillow image verification.
4. SQL Parameterization: Parameterized SQL queries throughout app/db.py eliminate SQL injection risks.

Key Viva Q&A Highlights:
Q: Why use local OCR instead of cloud OCR APIs?
A: Cloud OCR transmits sensitive patient lab reports to external servers, violating medical privacy. Satarka processes all PDFs and images 100% offline using pypdf and Tesseract OCR.

Q: How does the 5-pillar validation score work?
A: Score = 0.30 * Relevance + 0.25 * Source Authority + 0.20 * Evidence Agreement + 0.15 * Recency + 0.10 * Domain Independence.

Q: What is the similarity threshold for a dataset vector match?
A: 0.88 Cosine similarity in FAISS vector index.

Q: How is local LLM fine-tuning implemented?
A: Using 4-bit NF4 BitsAndBytes quantization and PEFT LoRA (r=16, alpha=32) on Qwen2.5-0.5B-Instruct using Hugging Face TRL SFTTrainer.
